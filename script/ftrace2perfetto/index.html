1 · 怎么打开

不需要后端、不需要上传文件到任何服务器 —— Perfetto UI 是纯前端 WASM，trace 只留在本机。

STEP 1浏览器打开 ui.perfetto.dev
STEP 2点 Open trace file，选 iperf-lifecycle.pftrace（推荐）或 .json
STEP 3先看 iperf-zoom.pftrace（19 KB，秒开）熟悉箭头，再开全量看 26 s 全貌
两种格式的区别：.pftrace 是 Perfetto 原生 protobuf，加载更快、track 名完整、SQL 表干净； .json 是 Chrome Trace Event，通用、可用文本工具检查。两者事件模型一致，本次均已生成、均已通过官方校验。

5 · 轨道设计与关联规则

4 组 track

  • CPU 运行泳道（每 CPU 一条）：sched_switch 换入→换出，args 带 pid/tgid/prev_state/flags/runtime_ns/wake2run_us
  • 线程状态轨（每 tid 一条）：RUNNING / R / S / D / X / Z
  • IRQ / softirq 轨（每 CPU 一条）：硬中断、softirq、tasklet 画 slice；softirq_raise 画 instant
  • 进程生命周期（每 tid 一条）：fork / exec / wakeup_new / migrate / exit / free / wait 的 instant

怎么把两类 tracepoint 接起来

  • 按 tid 独立调度：iperf3-379 (371) [002] —— 短横后 tid、括号 tgid、方括号 CPU
  • 唤醒三兄弟：waking 决定唤醒 → wakeup 入队置 NEED_RESCHED → switch 才上 CPU；延迟从 wakeup 起算
  • 收包链：irq_handler_entry → softirq_raise(NET_RX) → softirq_entry → sched_waking → sched_wakeup → sched_switch；发包方向相反
  • prev_state：S/D 主动睡眠，R/R+ 被抢占
  • free 的坑：被释放的 task 只在 args 的 comm=/pid= 里，行前缀常是 <idle>

6 · SQL 查询模板

在 Perfetto UI 左侧 Query (Trace Processor) 面板粘贴，或用 trace_processor_shell query <file> "<sql>;"。

-- 各进程占用 CPU 时长 TOP 10
SELECT s.name, count(*) AS slices, round(sum(s.dur)/1e6, 2) AS ms
FROM slice s JOIN track t ON s.track_id = t.id
WHERE t.name LIKE 'CPU%' AND s.dur > 0
GROUP BY s.name ORDER BY ms DESC LIMIT 10;

-- 唤醒延迟（key 前缀：proto 是 debug.，JSON 是 args.）
SELECT count(*) n, round(avg(real_value),1) mean_us,
       min(real_value) min_us, max(real_value) max_us
FROM args WHERE key LIKE '%wake2run_us';

-- 六类生命周期事件计数
SELECT name, count(*) FROM slice
WHERE dur = 0 AND name LIKE 'sched_process%' GROUP BY name;

-- 主动睡眠 vs 被抢占
SELECT string_value AS prev_state, count(*) n
FROM args WHERE key LIKE '%prev_state'
GROUP BY string_value ORDER BY n DESC;
格式差异：原生 .pftrace 的 track 名在 track.name、参数 key 前缀是 debug.； Chrome JSON 的 track 名可能为空（需 join thread_track / thread）、参数 key 前缀是 args.。 上面用 LIKE '%xxx' 兼容两者。
